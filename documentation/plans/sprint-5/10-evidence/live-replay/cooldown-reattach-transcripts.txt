## Build cooldown, operator route (AC-10-26)

SRT stock_balance finished (extractedAt 2026-09-20T10:04:54.813684Z). At 2026-09-20T10:05:38Z
(44s later, inside the 60s window):

    POST /autocount/pull/snapshots {"companyId":"<SRT>","entityType":"stock_balance"}
    -> HTTP 429
    {"detail":"A snapshot for this entity was built less than 60 seconds ago. Try again shortly."}
    Retry-After: 16

16s remaining matches 60 - 44 = 16 exactly.

NOTE: the S6 brief text said "-> 409 with the A6 code" for this probe; the ACTUAL, code-defined
status for both the operator route (`PullBuildCooldownError` -> `routers/pull.py`'s `_raise`) and
the gateway (`PullGatewayError(429, "TOO_MANY_BUILDS", ...)`) is 429 Too Many Requests, not 409 -
409 is reserved for `PUSH_ACTIVE`/`PULL_NOT_ENABLED`/`AMBIGUOUS_COMPANY`. Recorded as a brief-text
correction, not an application defect (the code and the plan's own Appendix A6 agree on 429 for
`TOO_MANY_BUILDS`).

## Gateway-triggered BUILD (not just read) - SRT product, fresh extraction

    2026-09-20T10:05:55Z
    POST /api/v1/autocount/snapshots {"companyCode":"SRT","entity":"products"}
    X-API-Key: <key>
    -> (blocked for 8m47.86s - see README "Gateway event-loop-blocking defect")
    HTTP 202
    {"snapshotId":"c52df8df-6999-4097-825b-5e150e223692","status":"ready","entity":"products","companyCode":"SRT"}

Note the response body's `status` is already `"ready"` on a `202 Accepted` - because, by the time
the HTTP response is constructed, the entire synchronous build already completed inside the same
request/coroutine. A conventional `202 Accepted -> poll for ready` client would not expect this.
