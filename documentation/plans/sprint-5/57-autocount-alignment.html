Before every operation the service checks, and refuses without writing anything when one fails: same item and unit; the SO line still needs that qty; the PO line is not on a Shipping PO; the received qty is known (section 3); nobody else is writing that document right now; the document has not changed since the CRM read it; the idempotency key is new (a repeated key returns the first answer and writes nothing).

Split link: give 5 of row 12043 to SO row 12041 WORKS TODAY

  1. One edit: cut row 12043 from 35 to 30 and add a new 5 row linked to SO row 12041, in the same call. AutoCount puts the new row at HQ. C03, C08
  2. Move the new row to BRW-AM (the SO line's location). P4 If the move fails: the link stands; answer "done, location not moved"; the user retries the move.
  3. Answer the CRM with what AutoCount read back, and push the refreshed PO to the CRM.

Link whole line: row 12044 (10, HQ) to SO row 12041 WAITING AUTOCOUNT DELETE

Today AutoCount answers 200 but ignores a link on an existing line (P10a), and has told us a link can never be changed on an existing line.

  1. Keep a snapshot of row 12044 (every field).
  2. Delete row 12044. If it fails: nothing changed; answer "refused" or "AutoCount error".
  3. Add a new row: same item, qty, price, description, delivery date, linked to SO row 12041. AutoCount puts it at HQ and gives it a new row number. If it fails: recovery adds row 12044's copy back (unlinked, HQ). Answer "recovered": the line is as before, under a new row number.
  4. Move the new row to BRW-AM. If it fails: answer "done, location not moved".
  5. Answer: "row 12044 is now row N", and push the PO with "row N replaces row 12044" (section 4).

Unlink: free row 12046 (10, BRW-AM, linked to SO row 12039) WAITING AUTOCOUNT DELETE

  1. Snapshot row 12046.
  2. Delete row 12046.
  3. Add a new 10 row at BRW-AM with no link. If it fails: recovery adds the linked copy back (lands at HQ) and moves it to BRW-AM. Answer "recovered".
  4. Answer "row 12046 is now row N"; push the PO.

Relink: move row 12048 (5, linked to SO row 12040) to SO row 12041 WAITING AUTOCOUNT DELETE

  1. Snapshot row 12048, delete it, add a 5 row linked to SO row 12041 (lands at HQ), move it to BRW-AM.
  2. If the add fails: recovery re-adds the old link to SO row 12040 and moves it back to BRW-AM.
  3. If row 12048 were on a Shipping PO line, the relink is refused until that SPO line is released first (plan 55 rule kept).

When recovery also fails: "needs attention"

If the line was deleted and both the new line and the re-created original are refused, AutoCount no longer has that line. The service then: marks the operation needs attention; keeps the snapshot; emails the AutoCount alert recipients once, naming the exact line to re-key (e.g. "PO FXT-1104d-1: SRTKT38SS 10 UNIT at BRW-AM, linked to FXT-1104d-SO row 12039"); never retries on its own. A Resume action reads AutoCount again and re-creates the line only if it is still missing, so a lost answer can never double a line.

3Received and delivered lines (owner ruling Q2 a)

Rule. A line fully received (GRN) or delivered (DO): refuse "line already received". Partly received: never delete; cut the original line to the received qty (it keeps its current link) and put the open remainder on a new line with the new link (or none). Received qty not readable exactly: refuse "receipt state unknown". A one-line switch can change this to "refuse any line with any receipt".

Worked example (illustration on row 12043; db3 has no goods receipts): row 12043 holds 35, 20 already received. Relink it to SO row 12041:

  1. Edit row 12043 from 35 to 20 (the received 20 stay as they were).
  2. Add a new 15 row linked to SO row 12041 (lands at HQ), then move it to BRW-AM.
  3. No delete is needed, so this path works with today's API once the received qty is known.

If all 35 were received: refused. If the received qty cannot be read: refused.

Important for timing. AutoCount's read API does not return a line's received or transferred qty today (AQ11). By this rule every link change on a db3 / API-sourced document is refused "receipt state unknown" until AutoCount adds that field, even after the delete door ships. Live companies read over SQL do carry it.

4Row numbers change: how the CRM keeps up

Delete + add gives the line a new row number (DtlKey); so does a recovery. Anything the CRM pinned to the old row (reservations, link claims, notes) must move to the new one. Two paths, both built (owner Q3 a):

  1. The answer to the CRM's call lists "old row 12044 is now row N".
  2. The PO pushed to the CRM marks the new line "replaces db3:12042:12044", so CRM ingest moves the pinned state itself even if the CRM's call timed out. This is a new optional field (Sorento contract 2.12); the CRM side is a later CRM lane.

5Switches and how they reach CRM buttons

Each (document, primitive) has an on/off switch in shared-service code, never a setting: create / edit / add line on for quotation, sales order and purchase order; delete line, delete document and cancel off everywhere; Shipping PO create and add line off. Turning one on = a code change, a review, and a recorded db3 run.

Proposal (to build with the gateway slice): the shared service publishes, per company, which operations are available and why not (e.g. "Link whole line: waiting for AutoCount delete"). The CRM Stock Debt screen (lane AC-LINK-CRM-UI, CRM PR #2168, at plan stage) shows only the buttons that will work, and a disabled one says why. When AutoCount ships delete and we flip the switch, the buttons light up with no CRM release. The shared service still refuses anything switched off, as a safety net.
