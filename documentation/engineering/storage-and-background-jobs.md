### Storage provider migration + centralized background jobs (LIVE since sprint-4/10 - closes BL-077)
Closes BL-077. Plan `documentation/plans/sprint-4/10-storage-migration.md` (+ `-acceptance-criteria.md` + `-test-report.md`). Verified end-to-end via a moto-backed A→B migration through the UI (upload → migrate → old asset resolves from B + new upload works). **Deploy this feature with `bootstrap_db`, NOT `init_db`** - `create_all` can't add `is_active` to the pre-existing `connections` table (the migration is correct; init_db just doesn't run it).
- **Bucket switch = transient A→B, never edit-in-place.** Because blobs are keyed `conn:<connection_id>:<raw>` and reads route by the KEY's connection id, reusing a connection id against a new bucket strands every historical asset. So migration: create connection **B**, flip the storage write-target to B, mark **A `is_active=false`** - all in ONE txn at START. New uploads land on B immediately; A is frozen + only DRAINED (its snapshot copied). Reads serve from A (old keys) and B (new keys) throughout - zero downtime. Cutover = **batch value-checked rewrite** `conn:A:`→`conn:B:` (`WHERE col LIKE 'conn:A:%'` - a row re-pointed mid-run is already `conn:B:` so never clobbered). A lingers inactive (audit + serves failed stragglers); its bucket contents are NEVER touched by us.
- **`is_active` on `connections` unifies retire + transient coexistence + write-target.** "Active storage connection" = the single `is_active=true` storage row → `resolve_for_type` filters `is_active`; resolve-by-KEY (`get_by_id`) ignores it (retired A still serves). Unique index relaxed to `WHERE type != 'payment' AND is_active`. The write-target flip IS the `is_active` flip (no extra pointer column).
- **Copy must PRESERVE the raw path** - `save()` mints a fresh uuid → WRONG for copy. New adapter `put_raw(raw, content, mime)` writes at the EXACT key; then rewrite is a trivial prefix swap and resume needs no `{rawA→rawB}` map. **Continue-on-bad-blob** (missing source = record `failed`, skip, never abort; failed keys NOT rewritten, A NOT retired for them). **Partial cutover**: rewrite only successfully-copied keys; failures=0 → auto-cutover, ≥1 failure → HOLD at `needs_review` (explicit Complete/Retry). Orphans in B (mid-run replace/delete) ignored v1 (never served) - GC = BL-126.
- **`StorageKeyLocation` registry = the generic "find every stored key" seam** (mirrors StatusEntity/FactSource/ImporterDef). Scalar `*_key` columns register declaratively (`users.avatar_key`, `tenant_branding.*_key`, `import_jobs.*_key`, `documents.storage_key`, omnichannel `conversation_messages.media_key`, …); JSON-embedded keys (form `answers_json`, template block-docs) register a `rewrite_json` callback that **reassigns a fresh dict** (the SQLAlchemy in-place-JSON-mutation gotcha). Modules register their own locations at install. A **drift test hard-fails CI** if a `*_key` column is unregistered - the thing that actually saves future-you (loud at build, not silent at migration). Enumeration is **connection-scoped, not tenant-scoped**: a tenant-own connection's keys live only in that tenant's rows; the PLATFORM connection's keys span every fallback tenant → same code path sweeps both (tenant-own vs platform cross-tenant derived from `connection.tenant_id == PLATFORM_TENANT_ID`). Dedicated perm `integrations.migrate_storage` (+ grant sweep for existing tenants).
- **Centralized `background_jobs` table** (new core `public`) = generic `type`-dispatched job + worker + ONE "Jobs" activity drawer; storage migration is its FIRST `type`. Columns: `type/status/payload_json/result_json/cursor_json/progress_{total,done,failed}`; `register_job_handler(type, handler)`; eager-inline in dev, Celery in prod; atomic status-claim (import-engine double-commit guard); `cursor_json` = resume point; retention pruner in the beat task. Existing job tables (`import_jobs`/`document_download_jobs`/`workflow_runs`/`email_outbox`) LEFT UNTOUCHED (load-bearing/typed) - retrofit = BL-125. **When adding ANY new async worker-processed job, use `background_jobs` + a registered handler, not a new bespoke table.**
- **Job liveness = heartbeat, not status (fix/job-lease-orphan-sweep, prod incident 2026-09-07 16:59Z).** A blue/green deploy stops the old colour after a 30s drain; a 4-minute PO sync run cannot finish inside that, and `background_jobs.status='running'` is NOT rolled back on process death - the row stayed `running`, its `ac_sync_run` stayed open, every scheduler tick skipped the task ("still in progress"), and the old 60-minute `STALE_JOB_AFTER` only wrote a `JOB_STUCK` skip and paused; manual SQL was the only release. Now: `background_jobs.heartbeat_at` (nullable, no backfill - NULL falls back to `started_at`) is stamped by the worker in its OWN short transaction via `JobService.heartbeat(job_id)` (same shape as `workflow_runs.heartbeat_at`: one UPDATE on a connection off the session's bind, `SKIP LOCKED` on Postgres, best-effort - a failed heartbeat never fails the run) once per page and once per push batch of the autocount run. `JobService.fail_orphaned_running_jobs(older_than=settings.background_job_orphan_after_minutes, default 15, floor 5)` fails a RUNNING job whose `coalesce(heartbeat_at, started_at, created_at)` is older than that, with the error "Interrupted: the worker stopped (deploy or crash) before this run finished; the next run re-offers its staged rows", and fans out to every module's `on_job_orphaned(db, job)` bootstrap hook (discovered like `install_tenant`; core never imports a module) - autocount closes the open `ac_sync_run` (`FAILED`, same error, `finished_at`, `duration_ms`) and leaves staged rows alone. It runs at app startup (guarded) and from the scheduler, which now sweeps a stale in-flight job and proceeds with the tick instead of pausing the task; a FRESH in-flight job still skips the tick. Rule for any long worker job: stamp a heartbeat at every checkpoint, and let a sweep, not a human, release the orphan.
- **Build lessons (learned the hard way this slice - apply to any engine like it):**
  - **A data-backfill migration must NOT commit Alembic's own connection.** `Session(bind=op.get_bind())` + a per-batch `db.commit()` fires a real `COMMIT` on Alembic's migration connection mid-run and corrupts the `alembic_version` stamp on live Postgres (invisible to pytest - conftest is `create_all`, module Alembic is a Postgres-only no-op). Run a batched backfill on a **separate** `create_engine(settings.database_url)` connection (dispose it in `finally`); the revision must alter no schema so the side connection reads already-committed data. Every OTHER migration in the repo uses `op.get_bind().execute(...)` and lets Alembic's transaction commit at the end - match that.
  - **A long worker job that supports abort needs COOPERATIVE cancellation.** Eager-mode (dev/test) runs the handler inline with no interleave, so an abort-doesn't-stop-the-worker bug is INVISIBLE to the suite. The copy/work loop must re-read its own `status` fresh from the DB at each checkpoint (a concurrent abort committed `JOB_ABORTED` on another session) and bail BEFORE the terminal step - else the worker finishes and overwrites the abort. `db.query(BackgroundJob.status).filter(id==).scalar()` after each commit.
  - **`create_all` NEVER ALTERs an existing table.** Adding a column to an existing core table (`connections.is_active`) is invisible after `init_db` (which is `create_all`+seed) → the app 500s on the missing column. Reset/deploy a feature that adds a column with **`bootstrap_db`** (runs `alembic upgrade`), never `init_db`. The pre-existing `integrations.spec.ts` failing identically was the tell it was env, not code.
  - **A NEW module table does NOT auto-appear on a legacy `create_all` local DB - neither boot path materializes it.** `run_module_migrations` only `upgrade head`s when a `<schema>.alembic_version` row EXISTS; a legacy create_all DB has **no such row**, so it takes the *"no row + tables exist → stamp head, NO DDL"* adopt path (and if module Alembic never initialized at all - no `alembic_version` table - nothing runs). `install()`'s `create_all` runs on **first install only**, not every boot. Net for local testing: adding `idea_attachments` in migration 0007 + rebooting left the table absent → the Ideas read 500'd `relation "app_ideation.idea_attachments" does not exist`, surfacing as "Failed to fetch" in the FE. **Local fix before testing a new module table: run `IdeationBase.metadata.create_all(engine)` (or apply the migration DDL directly) - do NOT assume `next build`/uvicorn boot creates it on a pre-existing DB.** Prod is fine (deploy runs `bootstrap_db`/module upgrade on a version-stamped DB). Same family as the `create_all`-never-ALTERs bullet above and the `embed_connections` local-gap.
  - **A drift-test exclude-set is a decision-forcing seam, not a dumping ground.** `media_sample_key` (a REAL storage key) was parked in the exclude-set and would have silently never migrated; the drift test exists precisely to force "register it or justify the exclusion." Audit the exclude-set - a genuine key hiding there is a stranded-asset bug in waiting.
  - **Unit-test the backfill FUNCTION directly**, not just the migration wrapper - module Alembic doesn't run under conftest, so the function is the only thing pytest actually exercises; verify the migration wrapper separately on live Postgres.
  - **A backfill runs at ANY point in the migration chain's history, not just the day it was written - so it must be schema-tolerant, not just correctness-tolerant.** Prod incident 2026-09-06 (autocount module): migration `0006` queried the LIVE `AcCompany` ORM model - which by the time of a fresh `0001->head` replay carried `0007`'s/`0010`'s later columns - so `session.query(AcCompany)` inside `0006` raised `UndefinedColumn` on a connection still stamped at `0005`; separately, `0007`/`0008`'s shared `backfill_etl_defaults` helper named `ac_sync_run.added_count`/`updated_count` (columns `0008` itself adds), so even `0007` alone failed on a stamp between the two. `bootstrap_modules` swallowed both failures and let the container report healthy with the module frozen at a stale stamp and every write 500ing (BL-SS-101 proposes closing that swallow separately). The fix is two-layered: (1) a data migration that must stay queries a FROZEN `sa.table(...)` snapshot of only the columns it needs, never the live model (existing rule, restated); (2) a raw-SQL column/row backfill additionally inspects the LIVE connection first (`sa.inspect(bind).has_table`/`get_columns` - never the ORM model, which always reflects code HEAD regardless of which migration is running) and skips any table/column not there yet, so it degrades to a no-op at an earlier stamp instead of raising. Where a migration's ONLY job was seeding via the live ORM with no safe frozen-table equivalent, retiring its `upgrade()` to a documented no-op (keeping the revision id and chain position) and moving the same seed to a HEAD-safe per-tenant seed-if-absent hook is the right call over inventing a second copy of the seeding logic to keep in sync. Related trap (7bc1b5b0): a reflection call through `Session.get_bind()` inspects on a SECOND pooled connection - blind to the session's uncommitted DDL and rows, and under StaticPool SQLite its return to the pool rolls the caller's transaction back - so reflect through `session.connection()`.
