### Status & State-Machine Engine (LIVE since sprint-2/01 - the first platform engine)
Tenant-configurable state machines over the core `statuses` table - plan: `documentation/plans/sprint-2/01-status-engine.md`. Workflow/Rule/Template engines (BL-025/026/024) build on its seams.
- **Behavior = boolean trait flags** on the status row (`is_initial`, `is_terminal`, `is_active`, `blocks_access`, `is_archived`, `is_default`) - **never branch on `category`** (kept only as a cosmetic uppercase-key mirror for the tenant wire/filter; removal = BL-060d). Tenant `signin_allowed` reads `blocks_access`/`is_archived`; the archived list view filters `is_archived`. System rows: label/color/order editable, key/flags/delete locked.
- **ONE executor**: `app/services/status_machine.transition(db, entity_type, record, to_status_id, actor)` - strict edge graph (no edge = no move, no self-loops, terminal = no outgoing, no admin override), edge-role auth (`transition_roles` M2M, empty = unrestricted), notification dispatch in the SAME transaction (specs → recipients USER/ROLE/DYNAMIC(actor|assignee|owner) → inline merge-field render → plan-09 `email_outbox`; `IN_APP` modeled inert, BL-058), then emits `StatusTransitioned` via `app/events.py` (in-process seam - payload captured pre-commit; Workflow engine subscribes later). Every status change in the system must go through it.
- **Entity adoption = code-side registry** (`app/status_engine/registry.py`, mirrors the permissions.csv pattern): register `StatusEntity(entity_type, label, module, count_records, migrate_records, platform_owned?)` + a `status_id` FK on the table; modules append at install. Core registers `tenant` (platform_owned - operator-only). Backs `GET /status-entities`. Pending adopters: omnichannel BL-037, `User.status` BL-057.
- **Two-tier (D7)**: platform defaults carry `tenant_id NULL`; a tenant's FIRST EDIT forks the whole entity set (statuses + edges, records remapped). Reads resolve tenant fork else platform. Position-only canvas drags never fork (frontend persists positions only on an already-writable tier).
- **Tenant lifecycle rides the engine**: seeded edges active→suspended (Suspend), suspended→active (Reactivate), active/suspended→archived (Archive), archived→active (Restore - **archive is reversible** since sprint-2/02; hard delete = the separate purge below). Console lifecycle actions are **graph-driven** (edge label = button text, confirm copy from target flags) via `GET /platform/tenants/status-graph` (gated `tenants.read`, deliberately NOT `statuses.read`) + `POST /platform/tenants/{id}/transition` - whose permission derives from the TARGET's flags (`is_archived`→`tenants.archive`, else `tenants.suspend`) preserving the legacy boundary. Actions **group by LABEL, not edge** (mixed Active+Suspended selections bulk-Archive; each row fires ITS own edge). Tenant wire carries `statusId`/`statusLabel`/`statusColor` - render server label/color (colors are hex since the picker; legacy names map via `colorToHex`) - plus `availableTransitionIds` (per-record fireable edges, populated only while a conditioned edge exists).
- **Tenant hard delete (BL-035 closed)**: `TenantService.purge` - ARCHIVED-only (two-step safety), typed slug confirm, platform tenant refused; module teardown via `AppStoreService.remove_all_tenant_modules` (every module's `uninstall_tenant` hook, ACTIVE+INACTIVE) then core rows cascade FK-safe. `POST /platform/tenants/{id}/purge` gated platform key `tenants.delete`. Console: "Delete permanently" on archived rows (row+bulk; single types the slug, bulk types DELETE) via the shared `ConfirmActionDialog` typed-confirm contract (`ResourceAction.confirm.input`).
- **UI follows the Resource shell**: entity ResourceList → ResourceForm detail (Flow + Statuses tabs); the global **Edit toggle gates the canvas** (read-only by default). Generic canvas pieces in `components/platform/flow-canvas/` (`FlowCanvas`, dagre `layoutGraph` "Tidy", floating `OffsetEdge` - bowed pairs for opposite edges) are Workflow-engine-ready; `merge-field-editor` (chips + in-place preview) is the standard template-builder input (BL-024 adopts); `search-select` + `multi-select` are the ONLY dropdown primitives (every dropdown searchable - user mandate, sweep = BL-062). Engine perms: `statuses.read`/`statuses.manage` (core CSV).
- **Tests**: backend suite registers a synthetic `ticket` entity (`tests/test_status_engine.py`) - the reference for module adoption; E2E drags real connections on the canvas (drop ON the target handle; SVG edge-label clicks via `dispatchEvent`).
- **Polymorphic target_id rule** (learned via the sprint-2/01 review - an actual cross-tenant email leak): any stored reference to a user/role/record (`notification_recipients.target_id` and every future engine's equivalent) needs BOTH (a) save-time validation that the target belongs to the author's tier/tenant (422 otherwise) and (b) tenant-scoped resolution at use time (defense-in-depth against planted/corrupt ids). Never resolve a stored id with an unscoped `get_by_id`.
