### Workflow Engine (LIVE since sprint-2/08 - the fourth & LAST core engine; slices 08+09 MERGED)
n8n/Power-Automate-class automation: triggers → actions, evaluated via a topological executor. Plans: `documentation/plans/sprint-2/08-workflow-engine.md` (foundation, MERGED), `09-...-triggers-actions.md` (breadth, MERGED `9905f37`), `10-...-integration-polish.md` (closes BL-025/081/064, next). Built in **3 vertical slices** (one-plan-per-feature too big at ~3×) - slice 08 = thinnest end-to-end (manual trigger + email.send) to prove the whole stack; slices 09/10 fan out on the proven executor. **PLATFORM CORE, not an App Store module** (core auth/notification mail flows depend on it; modules EXTEND it by registering TriggerDef/ActionDef at install).
- **Doc = forever-contract graph** (`types/workflows.ts` mirror = `app/workflow_engine/schemas.py`): `{schemaVersion, nodes[], edges[]}` stored camelCase in `draft_definition_json`. DAG; node kinds trigger/action/**if** (IF lands slice 09 - executor built kind-extensible). `validate_definition` = the publish gate (one trigger as root / acyclic / orphans block / required-config), mirrored front (`lib/workflow-doc.ts validateDefinition` - keep PARITY incl. empty-array=missing) + back.
- **Execution = Celery-queued, run row is the source of truth** (`app/workflow_engine/worker.py`). **Dev/E2E/tests: eager runs INLINE on the request session** (`settings.celery_task_always_eager` - a worker process would open a different DB session and not see an in-test run; the service branches eager→`run_workflow(self.db, run_id)` else `.delay`). Conftest sets eager True. The executor (`executor.py`) does ONE topological walk writing `workflow_run_nodes`; a node failure halts the run + skips downstream (order-based skip is correct for linear v1 - slice 09's IF/fan-out needs descendant-based). `email.send` "succeeds" at ENQUEUE (D14) - delivery shows in the Email log, not the run.
- **Versioning/publish (D4)**: edit always writes the mutable **draft**; **Publish** snapshots draft → immutable `workflow_versions` row + sets `current_version_id` + denormalizes the trigger (`trigger_type/entity_type/action` cols for slice-09 event matching). Only the current version fires; **Run executes the DRAFT** (no publish needed, D13). `is_active` = plain bool (NOT the status engine), Settings tab. Runs **snapshot the executed graph** (`definition_snapshot_json`) so Logs replay is faithful after edits. Version history is its OWN paginated endpoint - NEVER embed the unbounded list in the workflow GET (same for runs).
- **Flat run-context (D7)**: dotted keys (`trigger.input.<key>`, `nodes.<id>.<out>`) so they merge-render through the template engine's `render_tokens` unchanged - substitution ONLY, **no eval/Jinja on tenant content** (anti-SSTI). String config fields render against it (`context.render_field`, escape=False for to/subject; custom-email body escapes merge values). Frontend dynamic-content picker (the `{ }` button) lists upstream node OUTPUT SCHEMAS and inserts the ref. Manual-trigger inputs = runtime params (key+label) collected by the Run dialog - NOT static values.
- **Registry (`registry.py`, mirrors StatusEntity/FactSource/TemplateContext)**: TriggerDef/ActionDef carry config schema + output schema + (actions) executor + `requires_connection`. Slice 08 = `manual` + `email.send` only. **Conditional fields via `NodeField.show_when=(field,value)`** (front mirror `showWhen`) - drives email.send's Template|Custom (bare-email) toggle; validate/required skip hidden fields. Actions own NO transport (email.send→`render_email`/bare-merge→`enqueue_raw(commit=False)`; the run owns the txn).
- **Action authority (D10)**: actions run as a synthetic Workflow actor, authorized AT PUBLISH (gated `workflows.manage`), NOT permission-checked per-run; tenant isolation NEVER relaxed (every query tenant-scoped - repos take `tenant_id`; cross-tenant = critical). Loop-guard (`triggered_by_run_id` chain + depth-5) columns carried, enforced slice 09.
- **Frontend = Resource shell + a workflow-specific canvas** reusing `FlowCanvas` (@xyflow/react) with custom typed nodes + ports (`components/platform/workflow-canvas/`). Tabbed form: **Editor** (toolbar Run/Publish/Unpublish + canvas) · **Logs** (n8n two-pane: run list ⇄ replay canvas + node-data inspector) · **Settings** (name/desc/Active) · **Versions** (paginated). **Debug-in-editor** OVERLAYS a run's data onto the current draft via `?debug=runId` nav (n8n - does NOT replace the draft; unrelated nodes stay), per-node staleness-aware Execute. **Click-to-add palette** (dnd-kit palette drag is NOT Playwright-drivable - click-to-add is the E2E path; canvas nodes target by `[data-node-type=...]`). Auto-connect-from-leaf was REMOVED in slice 09 (it forced wrong edges on IF branches - user feedback); nodes drop unwired and the author wires them. Undo/redo + non-destructive Tidy (BL-064) built in. Bulk list actions Publish/Unpublish/Archive/Restore/Delete + Active|Archived views.
- **Perms** `workflows.read/manage/run` (core CSV, granted to tenant Admin). **Migration `0b0a96337c3d`** - autogen needs `import app.models.utc_datetime` added manually (UTCDateTime columns). Tests: `tests/test_workflow_engine.py` (13 - validate matrix, executor, publish/version, run+enqueue, bare-email, archive/restore, debug, tenant scope, perm gate), `lib/workflow-doc.test.ts` (12), E2E `e2e/workflows.spec.ts` (2 + report). - **Slice 09 (triggers/actions breadth, MERGED).** Catalog fan-out: 6 triggers (`entity.created/updated/deleted`, `entity.field_changed`, `entity.status_changed`, `schedule.cron`) + 5 actions (`storage.put/get/delete`, `entity.transition_status`, `entity.update`) + the **IF node** (rule-engine branching). The executor's order-based skip became a **branch-aware active-set walk** (`run_workflow` - a node runs only if reached via a TAKEN edge; an IF activates only its true OR false targets, so the untaken branch's descendants skip). IF evaluates `evaluate(conditions, ctx)` - the condition-tree fact keys ARE the flat run-context dotted keys, pass `ctx` straight (substitution-only, no eval).
- **CRUD event bus (`app/workflow_engine/entity_events.py`, D1/D3/D5)**: `emit_entity_event(db, entity_type, action, record, *, tenant_id, actor, changes)` BUFFERS the event on the Session; a SQLAlchemy `after_commit` hook drains it. **The committed session is in 'committed' state and CANNOT emit SQL - drain on a FRESH `Session(bind=committed.get_bind())`** (key lesson; in StaticPool tests it shares the one connection, in prod a fresh pooled one sees committed data). Matching is INDEXED on the denormalized `trigger_type/trigger_entity_type` cols + in-Python refine (field_changed, status from/to). **Loop guard**: each run tags `db.info['workflow_origin']` (run/workflow/depth); a workflow already in the originating chain never re-triggers, `MAX_RUN_DEPTH` caps cascades. Services whose repo commits internally use `notify_entity_event` (emit + `dispatch_pending`); deletes emit BEFORE the delete commits. status_machine emits `status_changed`. **Triggerable-entity registry** (`entities.py`, mirrors StatusEntity): the v1 set (user/role/tenant/connection/template/workflow) = a fact source + tenant-scoped `load_record` + an `entity.update` writable whitelist. **`attr_for()` canonicalizes camelCase field keys → snake_case attrs** - the metadata/UI advertise camelCase but the whitelist + change-diff keys + columns are snake; normalize at the boundary or the whitelist's protection is incidental (and field_changed never matches multi-word fields).
- **CRITICAL - workflow dispatch must NEVER break the triggering request.** Event runs fire INSIDE the CRUD request's commit (eager dev). `dispatch_pending`/`_dispatch` are fully failure-isolated: each event commits independently, a failure rolls back + logs, nothing propagates - a broken/slow workflow can't 500 or block a user's create/update. Record facts are `_json_safe`-coerced before hitting the JSON run-payload column (a datetime fact once 500'd user-create AFTER the user committed).
- **Scheduler (`scheduler.py`, D9)**: `compute_next_run_at` (5-field cron + IANA tz → UTC, `croniter`); publish arms `workflows.next_run_at`; `run_due_workflows` is the minute-tick (guarded `UPDATE … WHERE next_run_at<=now` claim → enqueue → advance). **Wired via Celery `beat_schedule` (`workflows.run_due`, 60s) - needs a `celery -A app.workflow_engine.worker beat` process; eager dev has no beat** (call `run_due_workflows(db)` directly to test). `GET /workflows/metadata` (entities + tenant-resolved statuses w/ real ids + writableFields + `connections:{email,storage}`) backs the editor pickers; frontend metadata service is real-bound. **Storage action keys are tenant-authored → `_resolve_key` rejects `..`/absolute/`~`/NUL** (LocalDiskStorage joins onto the media root unsanitized; traversal = arbitrary file read/delete).
- **Editor UX (slice 09, heavy user iteration - see the design-language interaction principles below)**: searchable collapsed palette, unique editable node names + n8n "N nodes back" picker + quick-replace, right-click context menu, keyboard Delete, panels scroll to canvas height, missing-connection warning, raw-cron dropped, **NO auto-connect** (nodes drop unwired; wire by dragging handles - broke the slice-08 E2E, now updated; `connect` helper drives React Flow via `page.mouse`). Tests: `tests/test_workflow_triggers.py` (18), E2E `e2e/workflow-triggers.spec.ts` (event role-create real-clicks → run in Logs; workflow built via API setup to dodge flaky drag).

- **Status-notification vs workflow boundary (slice 10 D1)**: BOTH paths to "email on a status change" stay, rendering through the ONE `render_email`+outbox. A **transition notification** = the mail is PART OF the transition (same transaction, edge-authored, transition-local recipients - the load-bearing tenant-lifecycle path; keep its blast radius small). A **workflow** (`entity.status_changed` trigger) = the status change STARTS a multi-step/conditional/cross-entity orchestration (after-commit via the event bus, loop-guarded, observable in run Logs). Rule of thumb: one atomic transition-local mail → notification; branching/multi-step/other-entities → workflow.
