# Hand test - PR #180 SS-MIGRATION-SYNC (keep syncing from respond.io until cutover)

## URL
crew test copy

## Setup
- Schema change: module migration `0024_omni_migration_sync` (two new tables, `app_omnichannel.migration_syncs` and `app_omnichannel.migration_sync_hints`). The test copy boot runs it; if the tables are missing, run `python -m scripts.bootstrap_db` once.
- Sign in as a tenant Admin (holds `omnichannel_migration.manage`).
- A respond.io connection under Settings > Integrations that reads a SMALL respond.io test space (a few contacts with messages). respond.io is only read, never written. Its API address must be the normal `https://api.respond.io/v2`.
- A NEW empty workspace for this test (Omnichannel > Settings > Workspaces > New, name `Sync test <today>`). Do NOT use MyFuji Platform.
- The test copy runs Celery in eager mode (no beat). Where a step says "run the sweep", run this from `service_backend/` on the test copy:
  `.venv/bin/python -c "from app.database import SessionLocal; from modules.omnichannel.services.migration_sync_service import run_due_syncs; db=SessionLocal(); print(run_due_syncs(db)); db.close()"`
- You need a phone that can message one of the respond.io test space's channels (to create a new message on respond.io during the test).

## Steps
1. Sidebar: Omnichannel > Settings > Migration, click "New migration". Pick the test connection and `Sync test <today>`, map the channels (or leave them on "Skip for now"), click "Run dry run", wait, click "Start migration", wait for "Done".
2. On that migration's detail page, scroll below the report to the "Continuous sync" card. Note the respond.io contact count and "Full sweep about N min".
3. Click "Start syncing".
4. Read the status line.
5. From your phone, send "sync test 1" to the respond.io test channel. Wait until it shows in respond.io.
6. Click "Sync now". Wait about 10 seconds.
7. Sidebar: Omnichannel > Inbox, open that contact's conversation in `Sync test <today>`.
8. Back on the migration detail page, click "Copy" next to the webhook link. In a terminal: `curl -s -X POST -H 'Content-Type: application/json' -d '{"contact":{"id":<respond.io id of that contact>}}' '<pasted link>'`.
9. Run the same curl with the last character of the link changed.
10. From your phone send "sync test 2". Run the sweep (see Setup). Reload the conversation from step 7.
11. Click "Pause", then "Resume".
12. Click "Stop syncing (cutover)", confirm in the dialog, wait for the card to change.
13. In the step 7 conversation, look at the composer.
14. Resize the browser to 375 px wide on the migration detail page (the sync card), then back to 1280 px.

## Expected
- Step 2: the card shows "Start syncing" and the contact count equals the dry run's Contacts "Fetched".
- Step 4: status badge "Active"; the line reads "Syncing every 15 min. Last sync <time>: +0 contacts, +0 messages, 0 errors. Next sync <time>." (the first sync may already have run with +0).
- Step 6: "Last sync" moves to now and the line shows "+1 messages" (or "+1 contacts, +1 messages" if your phone was a new contact), 0 errors.
- Step 7: "sync test 1" is in the thread exactly once, at its respond.io time. The thread is NOT marked unread, and no workflow / AI reply fired in the Shared Service.
- Step 8: curl prints `{"ok":true}`.
- Step 9: curl prints `{"detail":"Not Found"}`.
- Step 10: "sync test 2" appears once (only the flagged contact was fetched; Last sync moved).
- Step 11: Pause shows badge "Paused" and the line says paused; Resume returns to "Active".
- Step 12: the card reads "Stopped <time>"; no Start/Sync now buttons except "Start syncing" to restart.
- Step 13: if the contact wrote within the last 24 hours the composer is open for free text (no 24-hour template lock); otherwise the template lock shows as before.
- Step 14: at 375 px the buttons wrap onto several lines, the webhook link is full width, no sideways page scroll; at 1280 px everything is on one row.
